## 1. 目标

M2 在现有 playback session-state foundation 上完成 Electron 2.0.2 的核心播放时序，同时保留当前 Bun Sidecar API 和 M9 transport Seam。完成结果固定为：

1. `PlaybackAudioRuntime` 成为 Audio 生命周期的 deep Module，独占 A/B deck、Audio Graph、owner handoff、fade、恢复探针和输出路由；
2. pending Audio Owner 与 committed Audio Owner 分离，任何异步结果都必须携带 generation 与 exact handle；
3. 同专辑相邻曲目可使用同一预载机制完成 gapless 或 720ms equal-power crossfade；
4. play、ready、stalled、Audio Graph 静音和输出设备失效均有可取消、有上限的恢复预算；
5. visual runtime 只消费只读 Audio Frame Source，不再创建、断开或恢复 `MediaElementAudioSourceNode`；
6. fade、gapless/crossfade 与输出路由使用 typed preference，并进入既有 `PreferencesRepository`；
7. 自动验证完成后，真实 WebView2 听感、设备和长时播放证据可标记为 `Field Validation Pending (non-blocking)`，不阻塞 M2 Code Complete。

## 4. 核心设计：PlaybackAudioRuntime deep Module

当前 Audio 生命周期分散在 `PlaybackRuntimeHost`、`PlayerController`、session runtime 和 visual composition。删除任意一层都不会消除复杂性，只会把 Audio 元素、Web Audio 节点、source identity、timer 和恢复知识散到更多 caller；这是 shallow ownership。

M2 将这些 implementation 收进 `apps/web/src/audio/playback-audio-runtime.ts`。它的 Interface 保持面向播放意图，不暴露 deck 数组、AudioContext、GainNode、timer 或 mirror element：

```ts
interface PlaybackAudioRuntime {
  load(source: PlaybackAudioSource, context: PlaybackLoadContext): void;
  play(): Promise<void>;
  pause(): void;
  seek(positionMs: number): void;
  setVolume(volume: number): void;

  prepareNext(request: PreparedPlaybackRequest): Promise<PreparedPlaybackHandle>;
  playPrepared(
    handle: PreparedPlaybackHandle,
    transition: PreparedTransition,
  ): Promise<CommittedPlaybackOwner>;

  setOutputRouting(preference: PlaybackAudioPreference): Promise<void>;
  listOutputDevices(): Promise<readonly AudioOutputDevice[]>;
  getActiveElement(): HTMLAudioElement | null;
  getAudioFrameSource(): ReadonlyAudioFrameSource;
  diagnostics(): PlaybackAudioDiagnostics;
  dispose(): void;
}
```

`PlayerController` 保留现有 `load/play/pause/seek/setVolume/on` compatibility Interface，并委托给该 runtime。现有 caller 可以逐步迁移，不需要一次改写所有播放业务。

该 Module 的 leverage 是：caller 只提交 source、handle、transition 和 routing preference，即可获得双 deck、Graph、fade、stale rejection、probe、device recovery 与 deterministic cleanup。删除它会迫使 Host、session runtime、visual 和 tests 各自重新理解这些规则，因此通过 deletion test。

### 4.1 Interface invariants

- 所有 `load`、`prepareNext` 和 `playPrepared` 都绑定单调 generation 与 exact handle identity；结构相同但不是原对象的 handle 无效。
- 任意时刻最多一个 Pending Audio Owner、一个 Committed Audio Owner 和一个 retiring outgoing deck。
- pending deck 的 `play`、`timeupdate`、`durationchange`、`ended`、`waiting`、`stalled` 和 `error` 不得直接更新 application store。
- `playPrepared()` 只有在 pending `play()` 成功且 authority 仍有效时才原子提交 owner；失败或 stale 时保留原 committed owner，并恢复 outgoing gain。
- committed owner change 是唯一能把对应 load 标为 `playing` 的媒体事件；原生 deck `play` 事件本身不是 authority。
- `dispose()` 幂等；dispose 后 handle、listener、timer、mirror、deck、Graph 和 frame source 均失效。

## 5. A/B deck 与 Audio owner

Runtime 创建两个长寿命 `HTMLAudioElement`，标记为 A/B。deck identity 在 runtime 生命周期内稳定，source 与角色可以改变：

```text
Deck A: committed ───────────────► retiring ─► idle
Deck B: idle ─► pending ─► committed ─────────────► ...
```

首次播放也走 pending → committed，只是没有 outgoing deck。普通手动切歌、quality reload 和 media recovery 可以重用 idle deck；同一 committed source 的暂停/恢复不得无故换 deck。

Application store 中的 selected/requested track 表示用户意图，不等同于 Audio owner。只有 runtime 的 committed owner handle 才能授权真实媒体时钟、ended、position、duration 和 audio-driven visual 状态。gapless prepared handoff 在 owner commit 后以一次 compare-and-commit 更新 queue/current track；旧 intent、非相邻 candidate 或重复完成均被拒绝。

### 5.1 Prepared handle

`PreparedPlaybackHandle` 至少绑定：

- runtime generation；
- outgoing `playbackSessionId` 与 `playbackIntentId`；
- candidate `trackKey`、queue index 与 queue fingerprint；
- deck identity 与 source identity；
- readiness 状态；
- `abort()`。

新用户播放意图、queue/mode 改变、source switch、quality change、stop、runtime dispose 或 candidate identity 改变都使 handle 失效。失效只清 pending deck，不暂停当前 committed owner。

prepared owner 被采用后，session runtime 必须消费一次性 adoption result，不得再次 resolve URL 或重新 load 已在播放的 incoming deck。

## 6. Audio Graph 所有权

`PlaybackAudioRuntime` 独占共享 `AudioContext` 和两个 deck 的 lifetime `MediaElementAudioSourceNode`：

```text
Deck A MediaElementSource → Deck A Gain ┐
                                        ├→ Mix Bus → Main Analyser → Master Gain → Destination
Deck B MediaElementSource → Deck B Gain ┘          └→ Beat Analyser（只分析）
```

每个 Audio 元素在同一个 live context 中只调用一次 `createMediaElementSource()`。deck 切换只修改 gain 和角色，不断开另一 deck 的 source；因此 crossfade 期间 outgoing 与 incoming 都进入同一 analyser mix。

Graph ownership 从 `create-legacy-visual-composition.ts::initAudioSource()` 移出。Visual Module 获得 `ReadonlyAudioFrameSource`，其中只包含 main/beat frequency、time-domain bytes、sample rate、FFT size、committed media clock 与 playing 状态。Visual 不获得：

- `AudioContext`；
- `MediaElementAudioSourceNode`；
- deck 或 GainNode；
- `connect()`/`disconnect()`/`resume()`；
- output routing mutation。

这使 Visual 不可能因为 ref 提前切换而断开尚在淡出的 outgoing deck，也使 Audio Graph recovery 具备单一 Locality。

## 7. Gapless 与 crossfade

Gapless 与 crossfade 共享一个 prepared handoff，不实现两套竞争算法。

### 7.1 保守 eligibility

只有同时满足以下条件才创建 Album Gapless Candidate：

- `gaplessEnabled=true`；
- play mode 不是 `single` 或 `shuffle`；
- candidate 是当前 queue index 的严格相邻下一项；loop 仅允许显式的尾到首相邻规则；
- current 与 candidate 都有合法 provider、track id、album 和 cover URL；
- provider 相同；
- album 使用 `NFKC → trim → lower-case → collapse whitespace` 后相同；
- cover URL trim 后完全相同。

保守 album key 为：

```text
normalizedProvider + "\0" + normalizedAlbum + "\0" + trimmedCoverUrl
```

track identity 仍是 `provider:id`。任何字段缺失都视为不 eligible，禁止只凭标题近似、artist 或空 cover 猜测同专辑。

### 7.2 精确时序

| 参数 | 值 | 语义 |
| --- | ---: | --- |
| preload window | 8.5s | 当前曲剩余时间进入该窗口后才允许准备下一 deck |
| muted preroll window | 1.05s | 必要时以 0 gain/muted 激活 incoming decoder |
| equal-power mix | 720ms | 默认 crossfade 总时长 |
| minimum mix | 360ms | 尾部不足时的最小有效混合时长 |
| incoming attack | 56ms | incoming 快速达到安全 entry floor |
| owner adoption slew | 180ms | owner 提交后的 gain 收敛窗口 |

crossfade 使用 equal-power 曲线：

```text
outgoing = outgoingStart × cos(t × π / 2)
incoming = targetVolume × sin(t × π / 2)
```

`crossfadeEnabled=false` 时仍可预载，但不重叠可听输出；incoming 在边界成功 `play()` 后提交 owner。crossfade 启用时，incoming `play()` 成功并通过 authority check 后提交 owner，outgoing 进入 retiring，720ms 后暂停并清 source。

准备失败、ready 超时、`play()` reject 或 handoff stale 时，当前 committed owner 保持不变；普通 ended/next 路径兜底。prepared handoff 的失败不得消耗当前 media-error fresh URL budget。

## 8. Fade 与取消语义

typed preference 默认值：

- fade in：460ms；
- fade out：420ms；
- 有效范围：0–3000ms；
- equal-power album crossfade：720ms，由 handoff policy 固定，不与普通 fade 相加。

每个 fade 绑定 owner generation 和 cancellable serial。新播放意图、owner commit、seek-to-next、stop、volume envelope reset 或 dispose 会取消旧 fade；旧 callback 不得写入新 owner gain。

可见前台使用 AudioParam/RAF 推进。`document.hidden`、深后台或没有可靠 frame callback 时立即收敛到目标 gain，不等待被节流的动画完成。fade out 只有在 serial 仍有效时才 pause 原 owner；取消时不误暂停新 owner。

Audibility watchdog 在 520/1400/3200ms 检查 committed owner。只有媒体时钟前进、目标音量非零、没有 active handoff/seek 且实际 envelope 仍低于 floor 时才恢复 gain；每个 owner generation 各阶段最多一次。

## 9. 有界播放恢复

### 9.1 play/ready

- 每次 `play()` attempt 的 deadline 为 9000ms；timeout 与 reject 进入同一失败归一化路径。
- pending deck 因 ready 不足失败时，最多等待一次 `canplay` 后 retry；同一 generation 不允许第二次 ready retry。
- 新 generation 或 dispose 必须取消 deadline 和 `canplay` listener。

### 9.2 waiting/stalled

Runtime 监听 committed owner 的 `waiting` 和 `stalled`，但事件本身不立即刷新 URL。每个 load generation 安排 1600ms 与 3600ms 两阶段 probe，通过 currentTime、readyState、networkState 和 buffered end 判断是否真的没有进展。

- 进度恢复后清除该 generation 的 stall lineage；
- 每个 load generation 最多发起一次 fresh URL recovery；
- fresh URL recovery 继承同一 lineage 的总预算，禁止新 load 形成无限刷新链；
- local、trial、stale、paused、ended 和非 committed deck 不触发 fresh URL；
- 手动切歌、stop 与 owner change 取消旧 probe；
- exhausted 后进入现有可操作错误路径，不无限 spinner/retry。

existing long-pause、URL-age、quality 与 media-error policy 数值不变，并继续由 `PlaybackSessionCoordinator` 决定能否请求现有 `PlaybackPort`。

### 9.3 Audio Graph health

owner commit 后在 720/1600/2800ms 执行 graph probes。只有同时满足以下条件才把零信号判断为 Graph 故障：

- committed media clock 已越过启动区并持续前进；
- 连续两个 advancing sample 的 analyser signal `<= 0.0025`；
- AudioContext/source/analyser identity 仍属于当前 owner generation；
- 当前没有 pause、seek、ended、stale 或 target volume zero。

context missing/closed 可直接进入有界 rebuild；advancing-media-but-silent 只允许每 generation 一次 reconnect/replacement。冻结媒体时钟属于 media stall，不得误判为 silent Graph。rebuild 失败记录 diagnostics，并保留媒体事件/可操作错误，不形成无限重建。

## 10. 输出路由

### 10.1 Typed preference

`PLAYBACK_AUDIO_PREFERENCE` 使用现有 `PreferenceKey<T>` 与 `PreferencesRepository`，不新增 direct `localStorage` caller：

```ts
interface PlaybackAudioPreference {
  fadeInMs: number;                 // 0..3000，默认 460
  fadeOutMs: number;                // 0..3000，默认 420
  gaplessEnabled: boolean;          // 默认 true
  crossfadeEnabled: boolean;        // 默认 true
  primaryOutputId: string;          // "" = 系统默认
  mirrorOutputIds: string[];        // 去重，排除 primary，最多 4
  inputBridge: {
    enabled: boolean;
    deviceId: string;
  };
}
```

存储字段 `inputBridge` 为兼容命名；domain/UI 统一称 Virtual Output Bridge。它不是录音输入或 `getUserMedia` bridge，而是把已识别的虚拟音频输出设备设为 primary sink。

损坏值回到 typed defaults；mirror IDs trim、去重、最多四个且不能等于 primary。bridge enabled 必须有 deviceId；bridge 开启时其 deviceId 成为 primary 并从 mirrors 删除。

### 10.2 运行语义

- primary：Graph 可用时优先对 `AudioContext.setSinkId()` 应用；fallback path 对 committed/pending media element 应用，禁止双重可听输出。
- mirrors：最多创建四个 mirror Audio，复制 committed source、play/pause、volume、rate 和 position；每 2200ms 同步一次，仅当 drift `> 0.22s` 才 seek 纠偏。
- Virtual Output Bridge：复用 primary route，不创建额外 capture stream、进程或永久 timer。
- `navigator.mediaDevices.enumerateDevices()` 只在需要展示/刷新设备时调用；`devicechange` 触发列表 reconcile。
- primary `NotFoundError` 或已选 primary 消失时清为系统默认并持久化；bridge device 消失时禁用 bridge并回默认。
- mirror device 暂时消失时释放对应 Audio、保留可恢复 preference 与 unavailable diagnostics；设备重新出现时可恢复。
- `setSinkId` 不支持时 primary preference 可保存并显示 unsupported；mirror 不创建元素、不启动 timer。
- mirrors 为空、bridge disabled、primary default 且面板关闭时，输出路由路径不得保留 mirror Audio、sync interval 或额外 probe，disabled path 为零额外常驻资源。

## 11. State machine 与 React 接线

`PlaybackSessionCoordinator` 继续拥有 application session/load authority；`PlaybackAudioRuntime` 拥有 physical Audio owner authority。两者通过 exact `PlaybackLoadHandle` 和 ownerchange event 对齐：

```text
selected/requested Track
  → coordinator resolving
  → existing PlaybackPort resolves opaque source
  → audio runtime pending deck load
  → pending play succeeds
  → audio runtime commits owner
  → coordinator accepts exact ownerchange
  → store/UI/lyrics/position commit
```

非 owner deck 的 `playing` 不能把 reducer 推进到 `playing`。ownerchange 携带的 load handle 与 source URL 必须同时匹配 coordinator current load。source switch、quality reload 和 recovery 继续使用现有 session，而新的用户播放/stop intent 生成新 session。

`PlaybackRuntimeHost` 只创建、订阅和 dispose 一个 `PlaybackAudioRuntime`；不再自行管理多个 Audio/ref listener。`usePlaybackSessionRuntime` 编排 URL、歌词、queue 与 application state，不直接操作 deck、Graph、gain、sink 或 probe timer。

## 12. Deterministic diagnostics budgets

`diagnostics()` 返回不可变、可序列化 snapshot，至少包含 owner/pending/generation、Graph health、routing、probe/timer counts、recovery attempts 与最后错误 code；不得返回可变 DOM/Web Audio 对象或未裁剪的媒体 URL。

| 资源/动作 | 硬上限 |
| --- | ---: |
| primary decks | 2 |
| committed owners | 1 |
| pending owners | 1 |
| active handoffs | 1 |
| MediaElementSource / deck | 1 / live AudioContext |
| mirror Audio | 4 |
| play deadline | 1 / play attempt，9000ms |
| ready retry | 1 / generation |
| stall probes | 2 / load generation，1600/3600ms |
| fresh URL recovery | 1 / stall lineage |
| graph probes | 3 / owner generation，720/1600/2800ms |
| graph rebuild | 1 / owner generation |
| audibility probes | 3 / owner generation，520/1400/3200ms |
| mirror sync interval | 1，2200ms；disabled 时 0 |

architecture/performance tests 必须使用 fake clock、fake Audio、fake AudioContext、fake mediaDevices 和确定性 signal samples 证明上限；不以 wall-clock sleep 作为 PR gate。`dispose()` 后上述 current count 全部为 0。

- primary selected/ready/unsupported/unavailable；
